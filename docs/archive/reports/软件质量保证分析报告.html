智能答辩分组编排系统的质量保证工作分析

以自研应用「答辩安排助手」为例，说明质量维度、方法与实践，以及关键 SQA 活动的作用与实施方式

对象 Defense Scheduler v2026.10.02 技术栈 Vue 3 + TS / Django 6 + DRF / SQLite / PyInstaller EXE 日期 2026-10-09

核心结论：本项目的质量保证不是围绕"写得规范"展开，而是围绕四类高后果失效倒推建立——排期结果违反硬约束、并发编辑互相覆盖、数据迁移不可逆、桌面交付物与源码不一致。由此形成单一真相源 + 分层自动化验证 + 交付物级端到端核验三段式结构。

当前累计 243 项自动化回归全部通过，前端静态检查与构建、迁移多副本演练、打包 EXE 端到端验证均已通过并留有可复核记录。最大短板是没有持续集成——这套验证依赖人工按清单执行。

1项目画像与质量风险

质量保证的第一步不是选方法，而是判断"这个系统的失效长什么样"。本系统的特殊性在于：它输出的是一份将被真实执行的答辩现场安排表——出错不是页面显示异常，而是答辩当天导师到场、学生不在、专家撞场。

风险具体失效场景等级
R1 约束违反
算法输出错误		学生重复分组或遗漏；导师与自己学生同组（回避失效）；专家同时出现在两个组；时间/教室冲突；组长职称不达底线；正式答辩软件学院导师不足 3 人P0
R2 并发覆盖
多用户协同编辑		两名管理员同时改同一版本，后保存者静默覆盖前者；普通用户读到未发布草稿；重复提交产生重复版本P0
R3 迁移不可逆
schema 与数据演进		迁移改写基础数据关系时连带改写历史快照；升级失败无法回退；教师姓名匹配歧义导致关系错绑P0
R4 交付物漂移
源码 ≠ EXE		前端未重新构建即打包，EXE 内仍是旧界面；共享 JSON 未纳入打包导致运行缺文件P1
R5 结果不可解释算法给出"合规但反常识"的结果，教师不认可、不信任系统P1

2质量维度与优先级

优先级判据：不按 ISO/IEC 25010 的罗列顺序排，而按失效后果的不可逆程度排。本项目是低频、内网、小规模用户的内部工具，性能效率的战略权重远低于正确性与一致性；而一旦排期发布并被打印分发，纠错成本急剧上升。

由此得出：功能正确性 ≈ 数据一致性 > 安全性 > 可用性 ≈ 可维护性 > 可移植性 > 性能效率。

维度优先级在本项目中的含义主要保障手段
功能正确性P0 算法输出满足全部硬约束：学生覆盖、时间与教室互斥、不可用时间、角色资格、人数底线、导师同组/回避、正式答辩导师同场 243 项回归；可行性专项 SchedulingFeasibilityTests；生成与手调复用同一冲突检测入口
数据一致性P0 并发写入串行化；过期编辑被拒；已发布版本不可直接改；历史快照不被基础数据变更改写 全局写锁 + 事务；乐观锁 expected_revision（缺失 428 / 过期 409）；结果与导出快照冻结
可靠性P0 资源不足时不产出"看似成功"的错误结果，而降级为带错误标记的草稿；重复提交不产生重复数据 资源不足 → 待修复草稿且发布前重验阻止发布；request_key 幂等重试
安全性P0 认证与令牌过期、暴力破解限流、权限隔离、生产配置守卫、路径穿越防护 12 小时 TTL 令牌；失败 10 次/300 秒限流（缓存键经 SHA-256，不落明文）；生产模式密钥与 DEBUG 双守卫，不合格拒绝启动
可用性P1 非技术背景的教学秘书能独立完成排期；出错时能理解原因并知道如何修 五步向导（缺资料阻止继续、返回保留输入、刷新按 URL 恢复）；冲突面板逐条给原因与建议
可维护性P1 规则可评审可版本化；分层清晰便于替换算法；共享政策不让两端产生分歧 五层分层；scheduling/ 为不依赖 Django 的纯领域模块；policyVersion 显式版本化；政策外置为 JSON
可测试性P1 核心业务逻辑能脱离框架与数据库被独立、快速验证 领域规则纯函数化后用 SimpleTestCase（无数据库、毫秒级）
可移植性P1 既能源码运行，也能零依赖单文件交付给无开发环境的老师 环境变量驱动配置；SQLite → PostgreSQL 双引擎；打包配置显式声明依赖与数据文件；/health/ 探针
性能效率P1 生成请求在可接受时间内返回（前端超时 120 秒） 同步生成 + 幂等重试；主动取舍：写锁优先保证一致性，写操作串行等待

另有三个易被忽略、但本项目必须显式保障的维度：

  • 可复现性（确定性）——若算法用随机抽取，同一输入两次结果不同，管理员无法解释"为什么把张老师排到周三"，直接击穿 R5。故软件学院专家轮换采用确定性算法，不使用随机抽取。
  • 可审计性——排期涉及教师工作量与公平性，被质疑时必须能回溯"谁在何时改了哪一版、改前改后是什么"。故设服务端权威审计日志，与业务写在同一事务内。
  • 可恢复性——备份若本身不可信（如复制了正在写入的库），"有备份"反而更危险。故使用数据库在线备份接口从只读连接建一致副本，备份后强制完整性检查并生成哈希清单。

3方法与工程实践

3.1 三段式防线

① 预防 · 让缺陷不产生
  • 契约优先：接口契约先行，前端按 Mock 独立迭代
  • 单一真相源：政策与配色仅一份 JSON，两端只读
  • 业务规则外置为数据，不硬编码在分支里
  • 纯领域模块与框架解耦
  • 需求边界前置声明（含"未实现范围"）
② 检测 · 让缺陷当场暴露
  • 243 项后端回归（领域/契约/集成/迁移分层）
  • 前端领域测试（Node 直跑 TS 源码）
  • 静态门禁：类型检查 / ESLint / 迁移一致性
  • 黄金向量自校验：前后端哈希一致
  • 真实浏览器 UI 测试 + 打包产物端到端测试
③ 纠正 · 让缺陷可控可回退
  • 在线备份 + 完整性检查 + SHA-256 清单
  • 迁移多副本演练，源库哈希必须不变
  • 发布冻结：已发布版本不可直接修改
  • 生产配置守卫，不合格拒绝启动
  • 发布包哈希校验
需坦承的偏差：三段中投入最大的是检测，而工程上更优的状态应是预防占主导——缺陷发现越晚，修复成本越高。这是本项目一处明确的投入不平衡，第 5 节给出改进方向。

3.3 四项关键实践

实践做法解决的问题
单一真相源 +
黄金向量		 导师配色与哈希算法固化为唯一 JSON，内嵌 8 组"姓名 → 期望槽位"黄金向量；前端加载时自校验，漂移即输出指向两个待核对函数的控制台错误，后端测试覆盖同一组向量 把"两端实现一致"从口头约定变成机器可验证的不变式，防止同一导师在网页与导出中颜色不同、导致师生配对核对失效
契约优先 +
Mock 驱动		 接口契约先行并以类型定义为最权威参考；前端切到 Mock 模式单机迭代；发布构建强制关闭 Mock 与演示工具；分支分离，联调在专门分支完成后合入主干 把"联调才发现的不一致"左移到设计阶段；并避免演示数据静默回退掩盖真实后端故障
防御性设计
（质量内建）		 全局写锁串行化写入；乐观锁拒绝过期编辑且不保留部分写入；幂等键使重试不产生重复版本；发布快照冻结历史；生产配置不合格直接拒绝启动；用户输入进入打印页前转义 使并发覆盖、重复生成、历史篡改、误配置上线这几类问题在设计层面失去发生条件——测试只能证明"这一组输入正确"，结构才能保证"任意输入都安全"
迁移与发布
工程		 三级流程：合成样例 → 运行态副本 → 实际库备份后迁移；核验下沉到记录级（比对版本、组、专家关联、学生分组关联）；发布前重跑全量回归并直接启动打包产物验证；发布包不含数据库与密钥，附哈希清单 对冲 R3 与 R4。迁移是唯一"执行错误就无法靠回滚代码挽回"的环节；而源码更新不会自动替换已发放的旧产物

4关键 SQA 活动及其作用与实施方式

按介入时点排序，从需求到发布运维共 12 项。每项给出作用与实施方式。

活动作用（为什么做）实施方式（怎么做）
A1 质量目标与
验收标准定义		 在编码前确定"什么叫做好了"以及"用什么命令证明它做好了"。缺此步骤，后续测试没有判定基准，验收会退化为口头确认。 需求文档定义功能范围与业务底线；规则默认值外置为共享政策 JSON 并显式版本化；把验收标准固化为可直接执行的命令清单写入运维文档。
A2 需求与
设计评审		 在成本最低的阶段消除需求歧义与设计缺陷。"规则原文未说明"的边界若不在设计阶段暴露，必然变成上线后返工。 需求文档迭代修订并额外产出精简版对齐理解；架构文档以"已实现行为 + 尚未实现范围"双重口径描述系统；关键设计意图用边界测试守住，而非只写在文档里。
A3 分层测试设计与
自动化回归		 投入最大的活动。承担两项职责：证明当前版本行为正确，以及防止后续改动破坏既有行为（升级同时改动数据关系、规则语义与两阶段流程时尤为关键）。 按被测对象性质选择测试基类（纯逻辑用无数据库基类）；覆盖策略由风险驱动而非代码行驱动，落在契约、算法行为、规则效果、迁移正确性、稳定性与安全五个方向；回归按模块粒度执行，使"提交前跑一遍"时间可行。
A4 静态分析与
类型检查		 在运行前拦截整类缺陷，尤其是"模型与迁移不一致"这种本地正常、部署即崩的高危问题。 把类型检查嵌入构建链（构建脚本前置类型检查）而非当作可选步骤，使类型错误无法进入构建产物；代码检查采用 Vue 3 与 TypeScript 推荐规则集；后端以迁移一致性与系统检查作为门禁。
A5 一致性契约校验
（黄金向量）		 防止前后端对同一规则产生两种实现。哈希漂移会导致跨端语义失效，而这类问题普通测试很难自然发现。 唯一数据源内嵌黄金向量，前端在模块加载时自校验、后端测试覆盖同一组向量；后端哈希显式复刻前端语言的 32 位有符号截断语义并注明字符编码等价性。
A6 契约优先与
Mock 驱动的联调保证		 把"联调时才发现的不一致"提前消除；同时保证异常态（加载中、报错、空数据）被真正开发与验证，而非等联调才第一次遇到。 契约先定并以类型定义为最权威参考；前端在 Mock 模式下单机迭代；分支分离、联调在专门分支完成后合入主干；联调清单把异常态要求列为可勾选条目。
A7 安全评审与
安全机制验证		 排期数据含全体师生姓名与导师关系等个人信息，可能部署为内网多人服务，认证、授权、限流与配置安全须逐项验证。 令牌带过期时间并自动失效；普通用户只读已发布版本、不可读未发布草稿；登录失败限流且缓存键做哈希处理以避免明文入库；生产模式密钥强度与调试开关双守卫；打印视图对用户可控字段转义，测试以真实攻击载荷断言。
A8 数据迁移演练与
回滚验证		 直接对冲 R3。迁移是唯一无法靠回滚代码挽回的环节，必须在与生产同构的副本上先跑通，并证明演练未污染源数据。 用数据库在线备份接口从只读连接建一致副本，绝不直接复制打开状态的库文件；三级推进（合成样例 → 运行态副本 → 实际库）；核验下沉到记录级比对；备份目录同时保存数据库、哈希清单与应用密钥，并给出分步恢复流程。
A9 端到端与
验收测试		 验证"集成后是否真的可用"，并覆盖单元测试无法触及的失效：跨模块交互、真实浏览器行为，以及打包产物本身。 浏览器级用 Playwright 配独立临时库与随机端口跑全链路，断言浏览器错误数为 0；交付物级把打包产物复制到隔离目录直接启动，验证资源加载、首次迁移、政策、幂等、发布与导出、数据库完整性；另以真实名单与课表文件做导入冒烟。
A10 配置管理与
发布工程		 保证"被测对象 = 被发布对象"。源码更新不会自动替换已发放的旧产物，若不显式管理，代码级测试结论会与实际交付物脱节。 依赖分层声明（运行/生产扩展/验证工具），使"跑测试"与"跑应用"边界清晰；构建脚本检查外部命令退出码、清理产物前断言路径位于项目内以防误删；发布构建强制关闭演示数据；版本打标签并公示产物哈希。
A11 审计日志与
运行时可观测性		 测试只能证明设计时的正确性，无法回答生产环境中"谁改了什么"。审计与可观测性提供事后追溯能力，也是应对教师工作量质疑的客观依据。 审计写入与业务操作置于同一事务，失败请求回滚以保证不留下"成功"的审计记录；审计记录标记为权威，与浏览器本地日志区分；健康探针检查数据库连通性，故障返回 503；日志按大小轮转并给出监控建议。
A12 用户文档与
可用性验证		 面向非技术用户，可用性直接决定系统能否被真正采纳；"可复现步骤 + 真实截图"是证明系统按预期工作最直接的证据。 用界面结构承担防错职责（资料缺失阻止继续、返回保留输入、刷新恢复步骤），校规逻辑由前端领域测试断言；用冲突面板承担解释职责，逐条给出原因与建议而非只报"操作失败"；文档按使用者、升级、运维、维护者四类角色分册；以真实运行截图与分步复现流程佐证。

五项不足与改进建议（按投入产出比排序）

不足问题建议
1 · 无持续集成
最高优先		 243 项测试靠人工按清单逐条执行，形成一条脆弱长链，任一次"先跳过、回头再跑"都可能让缺陷进入发布；项目中确实没有 CI 配置。 以 CI 固化提交级门禁，至少覆盖后端回归、前端三项检查、迁移一致性检查、前端领域测试；打包与交付物测试作为发布标签触发的独立流水线。使"通过"从"这次记得跑了"变为"结构上无法跳过"。
2 · 无覆盖率与
属性测试		 用例数量是"计数"不是"覆盖度"；对启发式算法而言，最易出错的不是某条已知路径，而是"某种资源紧张的组合"，用增加固定用例几乎无法穷尽。 先引入覆盖率工具并对算法模块设门槛，让"未测到的分支"可见；再对硬约束引入基于属性的测试——随机生成师生、教室与时间约束，断言输出永不违反硬约束。这比再写几十个固定用例更契合启发式算法的质量特征。
3 · 类型检查偏松 类型配置关闭了严格模式与显式类型告警，而前后端字段映射、空值处理恰是此类项目的高频缺陷来源。 以类型定义目录与领域目录为试点逐目录开启严格模式，避免全量开启导致改动面失控；同时补充组件级单元测试（当前只有领域层脚本与浏览器端到端两端）。
4 · 无并发与
容量验证		 写锁串行化保证正确性但代价是写操作排队；文档亦自认未做长期负载与容灾压测，也没有"多人同时编辑"的并发测试。 设计最小并发用例：两个会话同时提交同一版本，断言一成功、另一收到 409 且数据未被部分写入；再以 500–1000 名学生规模测一次生成耗时基线，为"同步生成 + 120 秒超时"的取舍提供数据支撑。
5 · 无缺陷跟踪 项目有很强的"验证记录"（结果、哈希、耗时都留存），但没有缺陷本身的记录，包括已发现未关闭的需求缺口，质量数据无法用于趋势判断。 建立最小缺陷台账（编号、发现阶段、严重级、影响维度、状态），并在发布说明中列出"本版修复 / 仍保留"，与现有的"未实现范围"章节互补。

6结论

本项目的质量保证围绕四类高后果失效反向构建，形成三条实践主线：① 把不变式变成机器可验证的契约（单一真相源 + 黄金向量）；② 把正确性做进结构而非只做进测试（写锁、乐观锁、幂等键、快照冻结、配置守卫）；③ 把验证延伸到交付物本体（从纯领域单元测试一路做到打包产物直接启动验证，配合记录级迁移演练与源库哈希不变的硬证据）。

三大结构性短板同样明确：缺少持续集成这一"锁扣"，验证通过依赖人工纪律；缺少覆盖率与缺陷度量，用例数量无法等同于风险覆盖；对启发式算法最有效的属性测试尚未引入。其中属性测试与本项目"启发式求解 + 硬约束不可违反"的特征高度契合，投入产出比最高。

最后一点经验值得记录：本项目两次真实的质量教训都发生在单元测试之外（前端未重建导致产物内是旧界面、共享配置未纳入打包导致运行缺文件）。测试写得再多，如果被测对象不是交付对象，结论就是无效的。把验证锚定在"用户实际拿到的那份东西"上，是这个项目最值得保留的一条原则。

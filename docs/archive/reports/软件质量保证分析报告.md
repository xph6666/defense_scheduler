# 软件质量保证（SQA）分析报告

**分析对象**：智能答辩分组编排系统（答辩安排助手 / Defense Scheduler）v2026.10.02  
**技术栈**：Vue 3 + TypeScript + Element Plus ｜ Django 6 + DRF ｜ SQLite ｜ waitress ｜ PyInstaller 单文件 EXE  
**报告日期**：2026-10-09

---

## 核心结论（结论前置）

本项目的质量保证并非围绕"写得规范"展开，而是围绕**四类高后果失效**倒推建立——排期结果违反硬约束、并发编辑互相覆盖、数据迁移不可逆、桌面交付物与源码不一致。围绕这四点形成了"**单一真相源 + 分层自动化验证 + 交付物级端到端核验**"的三段式结构。

截至 v2026.10.02，累计 **243 项**自动化回归测试全部通过（后端 231 项 + 工程配置 12 项），前端静态检查与正式构建、数据迁移三副本演练、打包 EXE 端到端验证均已通过并留有可复核记录。

必须同时指出：**这套体系最大的结构性短板是没有持续集成**。243 项测试的执行依赖人工按清单逐条运行，缺乏自动化门禁把"通过"变成"不可绕过"。

## 1. 项目画像与质量风险定位

质量保证的第一步不是选方法，而是判断"这个系统的失效长什么样"。脱离失效后果谈质量维度，就会退化成对 ISO 标准的机械背诵。

### 1.1 系统概况

| 项目   | 内容                                                                                                                                             |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| 应用名称 | 智能答辩分组编排系统（答辩安排助手 / Defense Scheduler）                                                                                                         |
| 应用形态 | B/S 架构 Web 应用，同时以 PyInstaller 打包为 Windows 64 位单文件 EXE 交付                                                                                       |

| 业务域  | 研究生答辩排期，覆盖预答辩 / 正式答辩 / 中期答辩三类场景，含两阶段沿用                                                                                                         |

### 1.2 四类高后果质量风险

本系统的特殊性在于：它输出的是一份**将被真实执行的答辩现场安排表**。排期表出错的后果不是"页面显示异常"，而是答辩当天导师到场、学生不在、专家撞场、教室被占用。

| 风险类别                       | 具体失效场景                                                                     | 后果等级      |
| -------------------------- | -------------------------------------------------------------------------- | --------- |
| **R1 约束违反**（算法输出错误）        | 学生被重复分组或遗漏；导师与自己学生同组（回避失效）；一位专家同时出现在两个组；教室/时段冲突；组长职称不满足底线；正式答辩软件学院导师不足 3 人 | P0 · 现场事故 |
| **R2 并发覆盖**（多用户协同编辑）       | 两名管理员同时调整同一版本，后保存者静默覆盖前者；普通用户读到未发布草稿；生成请求重复提交产生重复版本                        | P0 · 数据丢失 |
| **R3 迁移不可逆**（schema 与数据演进） | 0008/0009 迁移改写基础数据关系，历史快照被连带改写；升级失败无法回到原状态；教师姓名匹配歧义导致关系错绑                  | P0 · 不可恢复 |
| **R4 交付物漂移**（源码与 EXE 不一致）  | 前端未重新构建即打包，EXE 内仍是旧界面；共享政策/配色 JSON 未纳入打包导致运行缺文件；打包顺序错误使修复未生效               | P1 · 交付失真 |
| **R5 结果不可解释**（业务可接受性）      | 算法给出"合规但反常识"的结果，教师不认可、不信任系统                                                | P1 · 采纳受阻 |

> **Echo 的判断**：R4 与 R5 是最容易被课程视角忽略、但在这个项目里真实发生过代价的两项。R4 属于典型的"构建管线质量"，它不是代码缺陷，却会让全部代码级测试的结论失效；R5 意味着**功能正确性不足以保证系统可用**——启发式算法的输出必须同时满足"约束成立"与"业务可解释"，这直接决定了后续要引入确定性轮换而非随机抽取。

## 2. 质量维度的构成与优先级

### 2.1 优先级的判定依据

本项目的质量维度优先级**不按 ISO/IEC 25010 的罗列顺序排列，而是按"失效后果的不可逆程度"排序**。理由很直接：这是一个**低频、单机/内网、小规模用户的内部工具**，日均请求量极低，因此"性能效率"的战略权重远低于"功能正确性"与"数据一致性"；反之，一旦排期发布并被打印分发，纠错成本急剧上升。

由此得到优先级：**功能正确性 ≈ 数据一致性 > 安全性 > 可用性 ≈ 可维护性 > 可移植性 > 性能效率**。这一排序直接体现在第 3 节的验证投入分配上。

| --------- | --- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |

## 3. 质量保证方法与工程实践

### 3.1 总体结构：三段式防线

| ① 预防 · 让缺陷不产生             | ② 检测 · 让缺陷当场暴露                                       | ③ 纠正 · 让缺陷可控可回退         |
| ------------------------- | ---------------------------------------------------- | ----------------------- |
| 契约优先：接口契约先行，前端按 Mock 独立迭代 | 243 项后端回归（领域/契约/集成/迁移分层）                             | 在线备份 + 完整性检查 + 哈希清单     |
| 单一真相源：政策与配色仅一份 JSON，两端只读  | 前端领域测试（Node 直跑 TS 源码）                                | 迁移三副本演练，源库 SHA-256 必须不变 |
| 业务规则外置为数据，而非硬编码在分支里       | 静态检查：`vue-tsc` / `eslint` / `makemigrations --check` | 发布冻结：已发布版本不可直接修改        |
| 纯领域模块 `scheduling/` 与框架解耦 | 黄金向量自校验：前后端哈希一致性                                     | 生产环境配置守卫，不合格拒绝启动        |
| 需求边界前置声明（含"未实现范围"）        | 真实浏览器 UI 测试 + 打包 EXE 端到端测试                           | 发布包 SHA-256 双文件校验       |

需要强调的是：**三段中投入最大的是第二段（检测）**，这在工程上并非最优——理想状态应是第一段（预防）占主导，因为缺陷发现越晚、修复成本越高。这是本项目一处明确的投入偏差。

> **Echo 的判断**：这套分层里，**真正体现质量意识的不是"有 243 个测试"，而是最后两层的存在**。多数项目做到"单元测试通过"就停止，但本项目两次真实教训都发生在单元测试之外：前端未重新构建导致 EXE 内是旧界面；共享 JSON 未纳入打包导致运行缺文件。把验证延伸到"交付物本体"，是 R4 风险倒逼出来的必要一步。

### 3.3 单一真相源 + 黄金向量：防"两端漂移"

本项目有一处设计上的必然约束：**导师配色必须在网页标签与 Word/Excel 导出中完全一致**，否则"同一导师同一颜色"这一视觉语义失效，而该语义正是管理员核对"师生配对 / 导师回避"的唯一抓手。这要求前端 JavaScript 哈希与后端 Python 哈希**逐位等价**。

解决方案是把色板与哈希算法一并固化为可校验的契约：

- `shared/mentor-colors.json` 是唯一数据源，含 16 个色槽（每槽 `light` 供网页底色、`dark` 供导出字体色），两端都只读这一份，任何一端都不得内联色值。
- 槽位统一由 `index = jsHash(导师姓名) % 16` 决定，因此同一导师在网页与导出中恒定同色。
- JSON 内嵌 `hashVectors`——一组**黄金向量**（8 组"姓名 → 期望槽位"）。前端 `src/utils/color.ts` 在模块加载时即自校验，一旦与后端实现漂移，直接在浏览器控制台报错并指出该核对哪两个函数；后端由 `MentorColorSourceTests` 覆盖同一组向量。
- 后端 `js_hash()` 显式复刻 JS 的 32 位有符号截断语义（每步 `h = (h * 31 + ord(ch)) & 0xFFFFFFFF`，末尾折算符号后取绝对值），并注释说明"中文姓名均为 BMP 字符，逐码位迭代与逐 UTF-16 码元迭代结果一致"。

这是一个成本极低、收益明确的实践：**把"两端实现一致"从口头约定变成机器可验证的不变式**。

### 3.4 契约优先与 Mock 驱动：把不一致左移

- **契约优先（Contract-First）**：后端接口未实现前，前端以 API 契约（URL、方法、Payload 结构、返回 JSON 格式）为准开发；契约记录在文档中，`src/types/` 下的类型定义被指定为接口最权威参考。
- **Mock 驱动单机迭代**：通过 `VITE_USE_MOCK` 切换，前端在 Mock 模式下完成全部交互、加载态与异常态开发。**并在发布构建中强制关闭 Mock 与演示工具**——这条很关键，否则"演示数据静默回退"会掩盖真实后端故障。
- **联调清单（Checklist）**：收敛为可勾选条目，包括环境变量切换、字段名一致性、异常态不崩溃，以及三项构建检查（`check` / `lint` / `build`）必须全部通过。
- **分支策略**：`feat/frontend-*`、`feat/backend-*`、`integration/*` 三类分支分离，联调在专门分支进行，通过后才合并回 `main`，以保证 `main` 稳定。

### 3.5 静态质量门禁

| 门禁命令                                         | 拦截的缺陷类型                                                                                  |
| -------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `vue-tsc -b`                                 | TypeScript / Vue 模板类型错误；同时作为正式构建前置步骤（`build` = `vue-tsc -b && vite build`），使类型错误无法进入构建产物 |
| `eslint . --ext .ts,.vue`                    | 代码缺陷与不安全模式；`vue/no-v-html` 保持 warn 级别，因为打印视图存在受控的富文本渲染需求                                 |
| `manage.py makemigrations --check --dry-run` | **模型与迁移不一致**——最隐蔽也最危险的一类：模型改了但忘记生成迁移，本地正常、部署即崩。要求输出 `No changes detected`                |
| `manage.py check`                            | Django 系统配置与检查项问题                                                                        |
| `git diff --check`                           | 空白字符错误与冲突残留                                                                              |
| `node scripts/test-frontend-domain.cjs`      | 前端领域逻辑回归（作为 `npm run test:domain` 暴露）                                                    |

### 3.6 防御性设计：把质量"内建"进运行逻辑

本项目一个值得强调的思路是：**相当一部分质量保证不是靠测试发现的，而是被设计成"不可能发生"**。测试只能证明"这一组输入下的结果正确"，而结构性机制能在全部输入下成立。

| 机制                   | 作用                          | 实现要点                                                                                                                             |
| -------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **全局写锁串行化**          | 消除并发写导致的丢更新                 | `ScheduleWriteLock(pk=1)` 在事务内以 `F('revision') + 1` 原子递增，且**必须作为事务内第一条查询**（否则 SQLite 锁升级时机错误）；副作用是写操作串行等待，文档明确说明这是"优先保证一致性"的主动取舍 |
| **乐观锁 revision 校验**  | 防止"基于过期数据的编辑"覆盖他人改动         | 提交必须携带 `expected_revision`：缺失返回 **428**，不匹配返回 **409**；被拒绝的提交通过 `transaction.set_rollback(True)` **不保留部分写入**                      |
| **请求幂等 request_key** | 网络超时重试不产生重复版本               | 同一 `request_key` 且规则一致的重试返回同一版本；标识相同但规则不符返回 409，防止"重试"被误用为"改参重生成"                                                                |
| **版本冻结快照**           | 历史排期不被后续基础数据变更篡改            | 发布/归档保存 `result_snapshot` 与 `export_snapshot`；已发布版本不可直接编辑，需调整则生成新草稿；姓名、关系、职称在快照中冻结                                               |
| **配置守卫**             | 误用开发配置上线导致的安全事故             | 生产模式下密钥短于 50 字符、或以 `django-insecure-` 等占位值开头、或 DEBUG 仍开启时，**直接抛异常拒绝启动**，而不是打一条警告日志                                               |
| **输入转义（打印视图）**       | 姓名/备注等用户输入进入 HTML 打印页时的注入风险 | 前端领域测试直接注入 `<img src=x onerror=alert(1)>` 与 `<script>` 断言输出被转义                                                                   |
| **登录限流**             | 暴力破解                        | 失败计数达 10 次即限流 300 秒；缓存键为 `sha256(客户端地址:用户名)`，**保证缓存中不出现明文账号**                                                                    |
| **路径穿越防护**           | 通过静态资源路由读取任意文件              | 使用 Django 的 `safe_join` 约束解析路径，越界抛 `ValueError` 后转为 404                                                                          |

### 3.7 数据迁移与发布工程

R3（迁移不可逆）是本项目风险最高的单点，因此采用"**先演练、后在生产副本上验证、最后才动真库**"的三级流程：

- **第一级 · 合成与副本演练**：通过 SQLite 在线备份 API 从只读源连接建立三个一致副本，分别覆盖"空业务表""运行态 30 教师 / 100 学生""独立合成样例（含 3 类旧规则 + 1 个已发布版本）"三种形态。副本全部完成迁移、`integrity_check` 与外键检查，且**源文件 SHA-256 保持不变**——这是"演练未污染源数据"的硬证据。
- **第二级 · 实际库备份 + 迁移后逐项核验**：对两个实际数据库各建一致备份后应用迁移，核验到记录级——100 个导师关系与 100 个秘书关系全部匹配，原 1 个版本 / 10 组 / 22 条专家关联 / 49 条学生分组关联**逐项与备份一致**。
- **第三级 · 发布验证**：发布前重跑整套 243 项回归（首轮 110.583 秒、发布前 96.942 秒），重新执行前端领域测试、静态检查与正式构建，再用 `scripts/test-exe-v2.py` 对被复制的 EXE 本体做端到端验证，并核对共享政策文件与 Word 默认模板确实进入了 EXE。
- **发布物控制**：发布 zip 仅含 EXE、使用说明与内部校验文件，**不含本机业务数据库、管理员凭据或密钥**；同时提供 `SHA256SUMS.txt` 供下载方核对。

打包配置 `DefenseScheduler.spec` 本身也是一份质量声明：显式列出隐藏导入（`waitress`、`docx`、`openpyxl`、`xlrd` 等）、显式排除测试模块与无关重依赖（`torch`、`tensorflow`、`pytest` 等）、显式声明数据文件（前端 `dist/`、共享政策与配色 JSON、python-docx 默认模板）；并在前端构建产物缺失时**直接报错退出**，而不是打出一个没有界面的空壳程序。


### 3.8 文档与可用性验证

文档在本项目中被当作质量资产而非附属产物，理由有二：一是**需求边界的显式声明**能防止"把未实现当作已实现"这一最严重的验收分歧；二是**面向非技术用户的操作说明**直接决定系统能否被真正用起来。

- **需求与架构文档**：PRD V1.0 → V1.1（含纯需求精简版），以及《V2 架构升级说明》，后者用 10 节分别描述模块分层、稳定关系、规则默认与业务底线、两阶段沿用、历史快照与导出、迁移演练结果、正式升级步骤、**当前保留的范围**、综合验证记录、打包与发布验证。
- **"未实现范围"专章**：明确列出评分汇总、外院人数分组阈值、跨校区整天联合预留尚未实现，并说明算法为启发式、不保证全局最优、资源不足仍可能产生待修复草稿。**把局限写清楚是质量手段，不是自曝其短。**
- **用户文档**：《教师快速上手》《分步向导与日程视图说明》《易用性升级说明》《稳定性升级与运维说明》，覆盖使用、升级、SQLite 恢复与多人服务器部署。
- **可用性实证**：《综合开发应用证明》附 8 张真实运行界面截图，并在文末给出可复现步骤。记录中还如实暴露了数据质量问题：冲突面板显示"错误 0 / 警告 10"，说明系统把"资源借用时间无法识别"这类问题如实暴露而非吞掉。

## 4. 关键 SQA 活动清单

以下 12 项活动按**介入时点**排序（从需求到发布与运维），每项说明：**作用**（为什么做）、**实施方式**（怎么做）、**本项目落地证据**（做到什么程度）、**局限**（哪里还不够）。

### A1 · 质量目标与验收标准定义（SQA 策划）

**作用**：在编码前确定"什么叫做好了"以及"用什么命令证明它做好了"。没有这一步，后续所有测试都缺少判定基准，验收会退化为口头确认。

**实施方式**

- 由 PRD（V1.0 → V1.1）定义功能范围与业务底线，并将规则默认值外置为 `shared/defense-policy.json`（`policyVersion: 2`，三类场景），使"业务底线"成为可评审、可版本化的数据而非散落在代码里的常量。
- 由《稳定性升级与运维说明》的"验收命令"一节把验收标准固化为可直接执行的命令清单。
- 规则版本显式化：前端 `policyVersion: 2` 经 `buildScheduleRules()` 转为算法字段 `policy_version: 2`，避免"新 UI 旧规则"这类静默不一致。

**落地证据**：`shared/defense-policy.json` 明确三类答辩的学生人数目标/上下限、专家总数与是否含主席、主席与秘书最低职称、导师回避开关、课程半天阻塞、正式答辩软件学院导师下限 3 人，以及 5 项软约束权重（0–100）。

**局限**：没有独立的、可量化的质量目标指标（如缺陷密度、覆盖率阈值、生成成功率），验收标准以"命令通过/不通过"的定性形式表达。

### A2 · 需求与设计评审

**作用**：在成本最低的阶段消除需求歧义与设计缺陷。本项目中大量"规则原文未说明"的边界（如"外院导师恰好 3 人时如何分组"）若不在设计阶段暴露，就一定会变成上线后的返工。

**实施方式**

- 需求侧：V1.0 到 V1.1 的迭代修订，并额外产出"纯需求精简版"用于对齐理解。
- 设计侧：《V2 架构升级说明》以"当前代码已经实现的行为 + 尚未实现的范围"双重口径描述系统，第 8 节逐条列出保留范围及其原因。
- 架构评审以可验证方式落地：`SchedulePolicyBoundaryTests` 断言领域层边界不被破坏，使"设计意图"变成会被测试守住的约束，而非写在文档里的愿望。

**落地证据**：《V2 架构升级说明》含模块分层图与逐层责任表（前端领域 / HTTP / 应用服务 / 关系与时间服务 / 导出 / 排期领域规则 / 算法兼容入口 / 持久化与一致性 / 共享政策），并明确说明哪些核心流程尚未从 `algorithm.py` 拆出。

**局限**：评审以单人自审为主，缺少独立第三方评审记录；"恰好 3 人如何分组"等歧义虽被识别并写入文档，但至今保留未决，属于已被发现却未被关闭的需求缺口。

### A3 · 分层测试设计与自动化回归

**作用**：本项目质量保证投入最大的活动。承担两项职责：**证明当前版本行为正确**，以及**防止后续改动破坏既有行为**——后者在 V2 架构升级中尤为关键，因为升级同时改动了数据关系、规则语义与两阶段流程。

**实施方式**

- 按被测对象性质选择测试基类：纯逻辑用 `SimpleTestCase`（无数据库、毫秒级），涉及持久化与 API 的用 `TestCase`。
- 测试命名用英文、断言消息用中文说明业务影响，使失败信息可直接被业务方理解。
- 覆盖策略由风险驱动而非代码行驱动：职责划分落在**契约、算法行为、规则效果、迁移正确性、稳定性与安全**五个方向。
- 回归范围按模块粒度执行（`manage.py test api` 约 100 秒；完整 `api defense_scheduler` 约 97–111 秒），使"提交前跑一遍"在时间上可行。

**落地证据**：241 项分布在 8 个后端测试文件（`tests.py` 107、`test_algorithm_v2.py` 43、`test_data_v2.py` 22、`test_architecture_v2.py` 21、`test_stability.py` 15、`test_recurring_time.py` 14、`test_auth_password.py` 5、`test_import_warnings.py` 4）+ `defense_scheduler/` 12 项 = **243 项全部通过**；另含 `RealDocumentSmokeTests` 使用真实课件文档做解析冒烟。

**局限**：① 无覆盖率度量，243 是"用例计数"而非"风险覆盖度"，`algorithm.py` 中未被触及的分支无从判断；② 未使用基于属性的随机测试，而启发式算法恰恰最适合用不变式检验；③ 缺少持续集成，全量回归依赖人工按清单执行。

### A4 · 静态分析与类型检查（缺陷预防）

**作用**：在运行前拦截整类缺陷，尤其是"模型与迁移不一致"这种本地正常、部署即崩的高危问题，以及接口字段拼写错误、模板类型不匹配等高频低级错误。

**实施方式**：把类型检查嵌入构建链而非当作可选的额外步骤——`build` 脚本定义为 `vue-tsc -b && vite build`，使类型错误在物理上无法进入构建产物；ESLint 使用 `vue3-recommended` + `@typescript-eslint/recommended` 规则集；Django 侧以 `makemigrations --check --dry-run` 与 `check` 作为门禁。

**落地证据**：验收命令与综合验证记录均包含 `makemigrations --check --dry-run` 输出 `No changes detected`、`manage.py check` 无问题、`git diff --check` 无空白错误、前端 `check`/`lint`/`build` 三项通过。

**局限**：`tsconfig.json` 中 `strict: false`、`noUnusedLocals: false`，且 ESLint 关闭了 `@typescript-eslint/no-explicit-any`，静态检查收益被显著削弱——类型系统最有价值的部分（空值安全、隐式 any）目前未被利用。

### A5 · 一致性契约校验（黄金向量）

**作用**：防止前后端对同一规则产生两种实现。本项目哈希漂移会直接导致"同一导师在网页与导出中颜色不同"，使管理员失去核对师生配对的视觉依据——这是一种测试很难自然发现的**跨端语义失效**。

**实施方式**：把"两端一致"提升为机器可验证的不变式。唯一数据源 `shared/mentor-colors.json` 内嵌 `hashVectors` 黄金向量；前端在模块加载时自校验（不一致时输出明确指向两个待核对函数名的控制台错误），后端由 `MentorColorSourceTests` 覆盖同一组向量；后端 `js_hash()` 显式复刻 JS 的 32 位有符号截断语义并注释说明中文 BMP 字符的等价性。

**落地证据**：`src/utils/color.ts` 的 `verifyHashVectors()` 在导入时无框架依赖地自执行；`api/mentor_colors.py` 明确声明"模块不内联任何色值，改配色只需改那个 JSON"；打包 spec 已将两个共享 JSON 列入 `datas`。

**局限**：同类"双端一致"约定目前只对配色落实了黄金向量；政策 JSON 虽有单一数据源，但缺少等价的向量化校验。

### A6 · 契约优先与 Mock 驱动的联调质量保证

**作用**：把"联调时才发现的不一致"提前到设计阶段消除；同时让前端不被后端进度阻塞，保证异常态（加载中、报错、空数据）也被真正开发与验证过。

**实施方式**：契约先定（URL / 方法 / Payload / 响应结构，并以 `src/types/` 类型定义为最权威参考）；前端以 `VITE_USE_MOCK` 单机迭代；分支分离，联调在专门分支完成后合入 `main`；每周 Demo 让后端直观理解接口的应用场景。

**落地证据**：《前后端协作与同步规范》定义了分支工作流、Mock 机制、字段变更通知机制与联调 Checklist；Checklist 明确列出"后端未启动、接口 4xx/5xx、空数据、保存失败时页面不崩溃"等异常态要求。

**局限**：Checklist 为人工勾选，无自动化校验；Mock 与真实后端的返回结构差异只能靠联调发现。

### A7 · 安全评审与安全机制验证

**作用**：排期数据包含全体教师与学生姓名、导师关系等个人信息，且可能部署为内网多人服务，因此认证、授权、限流与配置安全必须逐项验证，而非默认框架兜底。

**实施方式**

- 认证：自定义 `ExpiringTokenAuthentication`，令牌超过 TTL（默认 12 小时）即自动删除并抛出过期错误；未认证用户默认权限为 `IsAuthenticated`。
- 授权：`IsAdminOrReadOnly` 使普通用户只能读取已发布版本，写入操作限管理员；**普通用户无法读取未发布草稿**这一条写入接口兼容说明。
- 限流：登录失败计数达 10 次限流 300 秒，缓存键对"地址 + 用户名"做 SHA-256 处理以避免明文入库。
- 配置安全：生产模式下密钥强度与 DEBUG 双守卫，不合格拒绝启动；TLS、安全 Cookie、HSTS、CORS 均由环境变量显式控制（默认收紧），信任代理地址需显式指定。
- 输入安全：打印视图对姓名、教室、备注等用户可控字段做转义，并在前端领域测试中以真实攻击载荷断言。

**落地证据**：`test_auth_password.py`（5 项）、`SessionSecurityTests`、`AuthContractTests`、`PermissionContractTests`；`urls.py` 使用 `safe_join` 防护静态资源路径穿越；前端领域测试注入 `<img src=x onerror=alert(1)>` 与 `<script>` 并断言转义。

**局限**：无独立安全测试报告或第三方渗透测试；文档亦如实说明"本次没有连接实际 PostgreSQL、Redis 或 TLS 代理进行联调"，即在真实部署拓扑下的安全行为尚未被端到端验证。

### A8 · 数据迁移演练与回滚验证

**作用**：直接对冲 R3。迁移是本系统唯一"一旦执行错误就无法靠回滚代码挽回"的环节，因此必须在与生产同构的副本上先跑通，并证明演练未污染源数据。

**实施方式**

- 用 SQLite 在线备份 API 从只读连接建立一致副本，**绝不直接复制打开状态的数据库或 WAL 文件**。
- 三级推进：合成样例 → 运行态副本 → 实际库备份后迁移，逐级提升真实性。
- 核验下沉到记录级：不只看迁移是否成功，而是比对版本、组、专家关联、学生分组关联的逐项一致性。
- 保留回退路径：备份目录同时保存数据库、SHA-256 清单与应用签名密钥，并给出 6 步恢复流程（含"保留故障现场、不直接覆盖唯一副本""回退程序版本需匹配当时代码"等操作纪律）。

**落地证据**：三个演练副本（空业务表 / 运行态 30 教师 100 学生 / 独立合成样例）全部应用 `0009` 并通过 `integrity_check` 与外键检查，**源文件 SHA-256 不变**；两个实际库迁移后核验 100 个导师与 100 个秘书关系全部匹配，原 1 版本 / 10 组 / 22 条专家关联 / 49 条学生分组关联逐项与备份一致；`DataMigrationV2Tests` 提供代码级回归。

**局限**：实际业务库中没有 RuleConfig 记录，因此规则数据转换只能通过合成样例验证；文档亦承认"无法恢复升级前已经被删除或改写的信息"。

### A9 · 端到端与验收测试（含交付物级）

**作用**：验证"集成后是否真的可用"，并覆盖单元测试无法触及的失效——跨模块交互、真实浏览器行为，以及**打包产物本身**。这是 R4 风险的正面对策。

**实施方式**

- 浏览器级：`scripts/test-v2-ui.py` 使用 Playwright，配独立临时数据库与随机空闲端口，覆盖表单、政策、预答辩生成与发布、两阶段沿用与同场回避、秘书保留与显式改绑、历史版本打印、手机视图，并**断言浏览器错误数为 0**，结束前释放端口。
- 交付物级：`scripts/test-exe-v2.py` 把 EXE 复制到隔离目录后直接启动，使用独立数据库与随机端口，验证前端资源、首次自动迁移、角色政策、稳定关系、联排幂等、发布与导出、数据库完整性；通过 `psutil` 校验进程可执行文件路径确属本次测试副本后才终止。
- 真实数据级：以真实课表与名单文件做导入冒烟，暴露"借用时间缺失/无法识别"这类仅存在于真实数据中的问题。

**落地证据**：UI 测试在测试端口 8795 上以最新源码与构建完成，浏览器错误 0，截图与 PDF 保存在 `.tmp/v2-ui/`；EXE 测试对 `release/v2026.10.02/DefenseScheduler.exe` 全部通过。

**局限**：UI 与 EXE 测试同样是人工触发；未做大规模数据量下的端到端（压测）验证，也未覆盖多用户并发编辑的真实场景。

### A10 · 配置管理与发布工程

**作用**：保证"被测对象 = 被发布对象"。这是本项目付出过实际代价的环节：源码与 `dist` 更新不会自动替换已发放的旧 EXE，若不显式管理，所有代码级测试结论都会与实际交付物脱节。

**实施方式**

- 依赖显式声明并分层：运行依赖 `requirements.txt`、可选生产扩展 `requirements-production.txt`（PostgreSQL / Redis）、可选验证工具 `requirements-dev.txt`（Playwright / psutil），使"跑测试"与"跑应用"的依赖边界清晰。
- 构建流程加装失败即中断的守护：`build-exe.ps1` 检查外部命令退出码、校验 `vue-tsc` 是否存在、清理旧产物前先断言目标路径位于项目根目录内（**防止误删项目外文件**），最后断言 EXE 确实生成。
- 发布构建强制关闭 Mock 与演示工具（`VITE_USE_MOCK=false`、`VITE_ENABLE_DEMO_TOOLS=false`），避免演示数据在正式版中静默生效。
- 版本化与完整性：发布标签 `v2026.10.02`，提供 `SHA256SUMS.txt`，并对 EXE 与 zip 分别公示 SHA-256。

**落地证据**：`DefenseScheduler.spec` 显式声明 datas 与 hiddenimports，并在 `dist/` 缺失时 `SystemExit`；发布包经确认仅含 EXE、使用说明与内部校验文件，不含业务数据库、管理员凭据与本机密钥。

**局限**：代码版本控制、构建、打包、发布之间没有形成自动化流水线；`release/` 目录内并存多个版本产物，缺少产物清单与淘汰策略，存在取错版本的风险。

### A11 · 审计日志与运行时可观测性

**作用**：测试只能证明"设计时的正确性"，无法回答生产环境中的"谁改了什么"。审计与可观测性提供事后追溯能力，也是应对教师工作量质疑的唯一客观依据。

**实施方式**

- 审计写入与业务操作置于**同一事务**：`AuditedDataMixin` 在写操作完成后记录 before/after 快照；若响应码 ≥ 400，则 `set_rollback(True)`，**保证失败的请求不留下"成功"的审计记录**。
- 审计记录标记 `authoritative=True`，与服务端业务审计区分于浏览器本地日志——网页清空日志不会删除服务端记录。
- 资源编辑会使管理员已打开的草稿表单失效（递增当前草稿 revision），防止"基于过期资料的编辑"。
- 运行时可观测性：`/health/` 探针检查数据库连通性，故障返回 HTTP 503；`logs/server.log` 使用 5 MB × 5 份的轮转策略；文档给出监控建议（进程、磁盘空间、备份是否按时完成）。

**落地证据**：`OperationLog` 模型 + `api/audit.py`；`schedule_integrity.py` 的 `schedule_write` 装饰器在每次排期写入后记录操作类型、分组、版本与 before/after 结果；《综合开发应用证明》附操作日志界面真实截图。

**局限**：无指标（metrics）输出与告警机制，可观测性仅到日志与健康探针层面；审计日志无保留期与归档策略，长期运行会持续增长。

### A12 · 用户文档与可用性验证

**作用**：面向教学秘书这类非技术用户，可用性直接决定系统能否被真正采纳。同时，"可复现步骤 + 真实截图"是证明系统确实按预期工作的最直接证据。

**实施方式**

- 用界面结构承担防错职责：五步向导在资料缺失时阻止继续，返回时保留已填输入，刷新按 URL 恢复到原步骤——把"用户漏填"转化为"系统不接受"。前端领域测试以 `validateWizardRules()` 断言校规逻辑（如"校区独立开始日期必须落在总日期范围内"）。
- 用冲突面板承担解释职责：每次调整自动触发冲突检测（数据完整性、导师回避、专家重复、时间/容量冲突等），逐条给出原因与建议，而不是只报"操作失败"。
- 文档矩阵覆盖不同角色与场景：快速上手（使用者）、易用性升级说明（新版变化）、稳定性与运维说明（升级、恢复、部署）、架构升级说明（维护者）。

**落地证据**：《综合开发应用证明》含 8 张真实截图与 4 步可复现流程（含批量测试数据 教师 30 / 学生 100 / 教室 10）；《教师快速上手》《分步向导与日程视图说明》均已产出。

**局限**：可用性验证方式是"提供真实截图与可复现步骤"，而非有真实目标用户参与的可用性测试（无任务完成率、错误率等数据）；也没有用户反馈收集与缺陷跟踪闭环。

## 6. 局限与改进路线

按"投入产出比"排序，给出五项改进建议。前两项属于必须补齐的结构性缺口，后三项属于能力升级。

### 6.1 优先级最高：把门禁变成不可绕过

**问题**：243 项测试很强，但执行依赖人工按清单逐条运行（`manage.py test` → 前端三连 → UI 测试 → 打包 → EXE 测试）。这形成了一条脆弱的长链，任一次"先跳过、回头再跑"都可能让缺陷进入发布。项目内也确实没有 `.github/workflows` 或等效的 CI 配置。

**建议**：以 CI 固化提交级门禁，至少覆盖成本最低、收益最高的四项——后端回归、前端 `check`/`lint`/`build`、`makemigrations --check`、前端领域测试；打包与 EXE 端到端测试作为发布标签触发的独立流水线。这样"通过"才从"这次记得跑了"变成"系统结构上无法跳过"。

### 6.2 优先级次高：引入覆盖率度量与算法不变式测试

**问题**：231 项是一个**计数**，不是**覆盖度**。对启发式算法（`algorithm.py` 约 1375 行）而言，最容易出错的不是"某条已知路径"，而是"某种资源紧张的组合"——这类缺陷用增加固定用例的方式几乎无法穷尽。

**建议**：分两步。第一步引入 `coverage.py` 并对算法模块设置行/分支覆盖率门槛，把"未测到的分支"变成可见信息；第二步对硬约束引入**基于属性的测试**（如 Hypothesis）：随机生成教师、学生、教室与时间约束，断言输出**永不**违反硬约束（学生不重复、导师回避、时间教室互斥、资格与人数底线）。这比再写几十个固定用例更契合启发式算法的质量特征，也是当前最欠缺、性价比最高的补充。

### 6.3 收紧 TypeScript 严格性

**问题**：`strict: false`、`noUnusedLocals: false`，且 ESLint 关闭 `no-explicit-any`。前后端字段映射、空值处理恰恰是这类项目的高频缺陷来源，而类型系统最有价值的部分当前未被启用。

**建议**：以 `src/types/` 与 `src/domain/` 为试点开启严格模式，逐目录推进而非一次性全量开启，避免改动面失控；同时补充 Vitest + `@vue/test-utils` 的组件级测试（当前组件层没有单元测试，只有领域层 Node 脚本与浏览器 E2E 两端）。

### 6.4 补齐并发与容量验证

**问题**：写锁串行化保证了正确性，但代价是写操作排队，且文档已自认"未进行大规模列表分页、长期负载与容灾压测"。当前也没有针对"多人同时编辑"的并发测试。

**建议**：设计最小可行的并发测试用例——两个会话同时提交对同一版本的修改，断言一个成功、另一个收到 409 且数据未被部分写入；再以 500–1000 名学生规模做一次生成耗时基线测量，为"同步生成 + 120 秒超时"这一设计取舍提供数据支撑。

### 6.5 建立缺陷跟踪与度量闭环

**问题**：项目有很强的"验证记录"（验证结果、哈希、耗时都被记录下来），但没有缺陷本身的记录——包括已发现未修复的需求缺口（如"外院导师恰好 3 人时如何分组"原文未说明），以及每次发布修复了哪些问题。缺这一环，质量数据无法用于趋势判断。

**建议**：建立最小缺陷台账（编号、发现阶段、严重级、影响维度、状态），并在每次发布说明中列出"本版修复 / 仍保留"，与现有的"未实现范围"章节形成互补——前者管缺陷，后者管范围。

## 7. 结论

本项目的质量保证体系围绕四类高后果失效（约束违反、并发覆盖、迁移不可逆、交付物漂移）反向构建，形成了三条清晰的实践主线：

1. **把不变式变成机器可验证的契约。** 导师配色与哈希算法以单一 JSON + 黄金向量固化，使"前后端一致"不再依赖记忆；业务底线外置为 `defense-policy.json` 并显式版本化，使规则可评审、可回归。
2. **把正确性做进结构，而不只做进测试。** 全局写锁 + 乐观锁 + 幂等键 + 快照冻结 + 生产配置守卫，使并发覆盖、重复生成、历史篡改、误配置上线这几类问题在设计层面失去发生条件——测试只能证明"这一组输入正确"，结构才能保证"任意输入都安全"。
3. **把验证延伸到交付物本体。** 从纯领域单元测试、API 契约测试、前端领域 Node 测试，一直延伸到真实浏览器 UI 测试与**打包 EXE 的直接启动验证**，并配合记录级的迁移演练与源库哈希不变的硬证据。

同时必须承认其结构性短板：**整套验证缺少持续集成这一"锁扣"**，243 项测试的通过依赖人工纪律；**缺少覆盖率与缺陷度量**，用例数量无法等同于风险覆盖；**对启发式算法最有效的属性测试尚未引入**。这三点构成今后最应优先补齐的方向——尤其是属性测试，它与本项目"启发式求解 + 硬约束不可违反"的特征高度契合，投入产出比最高。

最后一点经验值得记录：本项目两次真实的质量教训都发生在单元测试之外（前端未重建导致 EXE 内是旧界面、共享 JSON 未纳入打包导致运行时缺文件）。**测试写得再多，如果被测对象不是交付对象，结论就是无效的。** 把验证锚定在"用户实际拿到的那份东西"上，是这个项目在质量保证上最值得保留的一条原则。

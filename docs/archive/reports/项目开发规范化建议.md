# 智能答辩分组编排系统：开发规范化建议

**文档性质**：工程治理建议书（不改动任何现有文件，仅提出规范与落地路径）
**分析对象**：智能答辩分组编排系统 v2026.10.02
**视角**：SQA（软件质量保证）· 软件系统分析与设计 · 项目开发管理
**日期**：2026-10-09

---

## 结论前置

这个项目已经具备**远超课程作业水平**的工程质量基础：243 项自动化回归全部通过、导师配色以单一 JSON + 黄金向量消除前后端漂移、全局写锁 + 乐观锁 + 幂等键把并发覆盖类缺陷从"靠测"变成"结构上不可能"、并已把验证延伸到打包 EXE 本体。**问题不在质量实践的水平，而在治理结构**。

三条最关键的判断：

1. **能力已具备，但缺少"不可绕过"的机制。** 质量实践靠人工纪律维持——测试跑不跑、跑哪几条、什么时候跑，全部依赖记忆与清单。没有 CI，就没有把"通过"从"这次记得跑了"固化为"系统结构上无法跳过"的锁扣。
2. **正确性做得很好，可追溯性几乎是空白。** 全仓库检索"需求编号 / REQ- / 验收标准 / 追溯"无任何命中：需求（散落在两份 .docx 与 WIKI.md）→ 设计（架构升级说明）→ 代码 → 测试之间**没有编号化的双向链接**。这意味着"这条需求做完了没有""这个测试在验证哪条需求"无法被机械回答，只能靠人复述。
3. **度量口径偏"计数"而非"覆盖"。** 243 是一个用例**数量**，不是**风险覆盖度**。对 `algorithm.py`（约 1375 行启发式求解）而言，真正的风险是"某种资源紧张组合下的约束违反"，这种缺陷用增加固定用例几乎无法穷尽。

因此本文的建议不追求"更规范的形式"，而是围绕**守住所建之物**展开：三个视角各补一件最缺的事——SQA 补门禁与度量，系统设计补契约与追溯，项目开发补节奏与配置管理。

> 说明：本文与仓库内已有的《软件质量保证分析报告》互补。那份报告回答"已经做了什么、做得怎么样"；本文回答"接下来按什么规范做、按什么顺序做"。两份文档不重复。

## 1. 三个视角的职责边界（先分清，再谈规范）

规范化最常见的失败是把三个视角混成一锅"要写文档、要写测试、要评审"的笼统口号。三者其实回答不同的问题：

| 视角 | 回答的问题 | 主要产物 | 失效时的后果 |
| --- | --- | --- | --- |
| **SQA** | 怎么**证明**做对了？ | 门禁、度量、审计记录、缺陷台账 | 缺陷进入发布，且无从判断严重程度 |
| **系统分析与设计** | 怎么让"对"**可以被构造**出来？ | 分层结构、接口契约、数据结构、不变式 | 复杂度失控，改一处坏三处，两端漂移 |
| **项目开发管理** | 怎么让"做对"**可以持续**？ | 需求基线、追溯矩阵、评审记录、版本与发布流程 | 范围蔓延、变更不可控、责任不清 |

**三者的耦合关系**：SQA 的门禁只能验证"设计暴露出的不变式"；设计暴露哪些不变式，取决于需求被拆到了什么颗粒度。所以**规范化必须自上而下**——先需求颗粒度，再设计契约，再质量门禁。反过来做（先上 CI 再补需求）会得到一堆"跑得很绿但不验证关键风险"的流水线。

## 2. 系统分析与设计视角：把不变式变成结构

### 2.1 已有优势（应保持并文档化）

这个项目在设计上做对了一件最关键的事：**把业务底线从代码里拿出来**。

- `shared/defense-policy.json` 承载专家人数、秘书配置、课程冲突等硬规则，并显式版本化（`policy_version: 2`）。
- `shared/mentor-colors.json` 用 16 槽位 + `index = hash(姓名) % 16` 决定导师颜色，配合 `hashVectors` 黄金向量，使"同一导师在网页与 Word/Excel 导出恒定同色"成为**可机器验证的契约**，而非约定。
- `api/schedule_integrity.py` 的 `schedule_write` 装饰器把写串行化、乐观锁校验、发布冻结校验、审计落库封装成一个横切关注点，而不是散落在每个视图里。

**这三条是本项目最值得保留的设计资产。** 规范化的第一步不是改造它们，而是把它们**登记为明确的架构决策**（见 2.4），防止后续维护者不知其存在而被绕过。

### 2.2 待改进一：分层边界需要"可执行"而非"可阅读"

当前分层已清晰（`views.py` / `schedule_views.py` → `api/services/` → `algorithm.py` 纯领域），但边界只存在于文档和开发者认知中，没有**机器检查**。风险是长期演化中视图层逐渐塞入业务逻辑。

**规范建议**：

1. 明确四层职责并写入 `开发文档V2/架构升级说明.md` 的显式契约：
   - **接入层**（`views.py`、`schedule_views.py`）：只做参数解析、权限判断、调用服务、包装响应；
   - **应用服务层**（`api/services/*.py`）：编排用例、事务边界、跨聚合协调；
   - **领域层**（`algorithm.py`、`scheduling/*.py`）：纯函数式求解与策略，不依赖 Django ORM；
   - **适配层**（`serializers.py`、`timetable.py`、`export_word.py`）：外部格式与内部模型的转换。
2. 引入 `import-linter` 或等效工具，将上述依赖方向固化为**可执行的架构测试**——"领域层不得 import `django.db`"应当是一条会在 CI 中失败的断言，而不是一条需要背诵的规矩。
3. `api/views.py`（约 33KB）与 `api/schedule_views.py`（约 35KB）已接近需要拆分服务的规模，建议在下次涉及这两处的功能变更时顺带按资源域拆分。

### 2.3 待改进二：把"隐式不变式"显式登记

系统中存在若干**没有写在任何契约文件里、但绝不能违反**的规则。例如：

- 预答辩场景下修改秘书会连带重绑学生（`schedule_integrity.py` 中有专门的判断逻辑）；
- 不能跨排期版本移动学生；
- 已发布/已归档版本不可编辑；
- `expected_revision` 缺失时应拒绝而非默认放行。
- 学生导师回避、导师不宜同组名单、秘书连续性等

**规范建议**：建立一份**不变式清单**（Invariants Register），逐条写明：编号、陈述、涉及模块、当前保障方式（结构约束 / 测试 / 人工）、验证用例位置。这份清单是三个视角的公共接口——设计视角在此登记，SQA 视角据此设计测试，开发视角据此评审变更影响面。

**优先级判断**：这是投入产出比最高的一项。因为它直接喂给下一节的属性测试与门禁设计，且几乎不需要改动运行代码。

### 2.4 待改进三：建立轻量 ADR（架构决策记录）

当前架构知识分布在 `架构升级说明.md`、`WIKI.md`、若干"XX 说明.md"与提交信息中，**没有统一的时间线**。典型例子：为什么选全局写锁而不是数据库行锁？为什么用 PyInstaller 单文件而不是普通打包？为什么 V2 要拆出 `scheduling/`？

**规范建议**：在 `开发文档V2/adr/` 下建立 ADR 目录，每条决策一页，格式极简：

```
# ADR-0007 写操作全局串行化
- 状态：已采纳
- 背景：SQLite 写锁升级易死锁，且并发编辑会互相覆盖
- 决策：ScheduleWriteLock 单行 + F() 自增，事务内首个查询完成锁升级
- 后果：正确性提升；写操作排队，吞吐受限
- 替代方案：数据库行锁（跨库行为不一致）、乐观锁单独承担（易产生部分写入）
```

**价值**：新人接手时不需要从提交历史里考古；评审变更时能判断"这次改动是否推翻了某条既有决策"。

## 3. SQA 视角：把"通过"变成不可绕过

### 3.1 已有优势（应保持）

- **分层测试按被测对象性质选择测试类型**：纯领域用单元测试（`api/test_algorithm_v2.py`）、接口用契约测试、前端领域用 Node 脚本直跑 TS（`scripts/test-frontend-domain.cjs`）、交付物用 EXE 直启验证（`scripts/test-exe-v2.py`）。这个策略是对的，且比"什么都用 E2E"成熟得多。
- **性能与稳定性有真实记录**：全量回归约 100 秒、迁移演练 5 个副本、源库哈希不变、EXE 启动全链路通过。
- **发布物有完整性证据**：EXE 与 zip 公示 SHA-256，且 zip 明确不含数据库与密钥。

### 3.2 待改进一（最高优先级）：建立持续集成门禁

**现状证据**：仓库内不存在 `.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile` 或 `.pre-commit-config.yaml`。243 项测试的执行完全依赖人工按清单逐条运行。

**为什么这是第一位**：现有质量资产的**全部价值**建立在"每次发布前真的跑了一遍"之上。一旦某次因为赶时间跳过，资产即刻归零。这不是纪律问题，是结构问题——**没有机制能让"跳过"变得不可能**。

**规范建议**（分两阶段，先易后难）：

**阶段一 · 提交级门禁（成本最低、收益最高，建议本周内落地）**

| 检查项 | 命令 | 拦截力 |
| --- | --- | --- |
| 后端回归 | `manage.py test api` | 阻断 |
| 迁移一致性 | `manage.py makemigrations --check --dry-run` | 阻断 |
| Django 系统检查 | `manage.py check` | 阻断 |
| 前端类型检查 | `vue-tsc -b` | 阻断 |
| 前端 lint | `eslint . --ext .ts,.vue` | 阻断 |
| 前端领域测试 | `node scripts/test-frontend-domain.cjs` | 阻断 |
| 空白字符 | `git diff --check` | 阻断 |

**阶段二 · 发布级流水线（由 tag 触发，与提交门禁分离）**

前端正式构建 → Playwright UI 端到端 → PyInstaller 打包 → EXE 直启端到端 → 生成 SHA-256 → 归档发布物。

**关键设计约束**：流水线必须能在**无人工干预**下跑通，即所有环境变量与依赖（Node 版本、Python 3.12、Playwright 浏览器）在流水线配置中固定。当前 README 要求 Node 18+，但 `package.json` 中 Vue 3.4 + Vite 5 的实际需求建议锁定到 Node 20/22 LTS，避免"本机能跑、CI 不能跑"。

> **注意**：本机环境 `npm`/`npx` 被安全策略拦截，流水线中的前端检查应直接调用 `node_modules` 内入口（如 `node node_modules/vue-tsc/bin/vue-tsc.js -b`），而非依赖 npm 包装器。

### 3.3 待改进二：从"用例计数"转向"风险覆盖"

**现状证据**：`tsconfig.json` 中 `strict: false`、`noUnusedLocals: false`；ESLint 关闭 `@typescript-eslint/no-explicit-any`；仓库内无 `coverage.py` 配置、无 Vitest、无任何覆盖率报告。

**规范建议**：

1. **引入后端覆盖率度量**：`coverage.py` 跑全量测试，先只做"可见化"（不设门槛），重点观察 `algorithm.py`、`api/services/` 的未覆盖分支。**先看数据再定门槛**，否则容易设一个所有人都选择跳过的形式化指标。
2. **对硬约束引入基于属性的测试（Property-Based Testing）**：这是本项目**最该做、也最被忽视**的一件事。
   - 工具：后端 Hypothesis，前端 fast-check。
   - 做法：随机生成教师、学生、教室、时间约束（含极端资源紧张组合），断言输出**永不**违反硬约束——学生不重复分组、导师回避生效、时间与教室互斥、人数与资格底线满足。
   - 理由：启发式算法的缺陷不在"某条已知路径"，而在"某种组合"。固定用例越加越多，覆盖的组合空间增长却极其缓慢；属性测试用少量断言即可覆盖巨大空间。
3. **分目录收紧 TypeScript**：不要一次性全量开启 `strict`（改动面会失控）。按 `src/types/` → `src/domain/` → `src/utils/` → `src/components/` → `src/views/` 的顺序逐目录推进，每次提交收紧一层。

### 3.4 待改进三：补齐并发与容量验证

**现状证据**：项目文档自认"未进行大规模列表分页、长期负载与容灾压测"。写锁串行化保证了正确性，但代价不明——排队延迟是多少、多少并发用户下会不可用，均无数据。

**规范建议**：

- **并发一致性测试**（必做，成本低）：两个会话同时对同一版本提交修改，断言一个 200、一个 409，且数据库未被部分写入；再测 `expected_revision` 缺失时返回 428 而非静默接受。
- **容量基线测量**（必做，成本低）：以 500 / 1000 / 2000 名学生规模各跑一次生成，记录耗时。当前"同步生成 + 120 秒超时"是一处设计取舍，这个取舍**需要数据支撑或推翻**。
- **长期稳定性**（可选）：长时间循环读写 + 观察 SQLite 文件增长与锁等待。

### 3.5 待改进四：建立缺陷台账与度量闭环

**现状证据**：项目记录了极强的"验证证据"（测试结果、哈希、耗时），但**没有记录缺陷本身**。已知未修复的需求缺口（如"外院导师恰好 3 人时如何分组"）散落在文档与对话中，没有编号、没有严重级、没有状态。

**规范建议**：建立最小缺陷台账，字段：`编号 | 发现阶段 | 严重级 | 影响质量维度 | 关联需求 | 状态 | 修复版本`。与现有《发布说明》的"未实现范围"章节形成互补——前者管缺陷，后者管范围。**不必引入重型工具**，一个 Markdown 表格 + 提交信息中的 `Fixes: DEF-012` 即可起步。

**度量定义建议**（避免自欺）：

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 缺陷逃逸率 | 发布后发现的缺陷数 / 本版总缺陷数 | 衡量门禁有效性，**唯一可信的质量趋势指标** |
| 门禁阻断次数 | CI 拦截的失败提交数 | 衡量门禁是否真的在被触发 |
| 算法分支覆盖率 | `algorithm.py` 分支覆盖 / 总分支 | 衡量启发式逻辑验证充分性 |
| 属性测试用例数 | 每轮随机生成的独立场景数 | 衡量约束验证强度 |

## 4. 项目开发视角：让"做对"可持续

### 4.1 已有优势（应保持）

- 提交信息规范度**高于平均水平**：`fix: resolve F-XX ...` 系列表明存在编号化的问题清单（F-01 至 F-09），这实际上已经是一份非正式缺陷台账——**建议将其正式化为 3.5 节的台账**。
- 版本与标签清晰：`v2026.09.19`、`v2026.10.02`，配套发布说明。
- 文档体系分层：PRD（V1.0/V1.1）、架构升级说明、运维说明、教师快速上手、WIKI，覆盖了不同读者。

### 4.2 待改进一：建立需求-设计-代码-测试追溯链

**现状证据**：全仓库检索"追溯 / 需求编号 / REQ- / 验收标准"**零命中**。需求存在于两份 `.docx`（PRD V1.0/V1.1、纯需求精简版）与 `WIKI.md`，但**没有唯一编号**。

**这是本项目在项目管理维度最大的结构性缺口。** 后果具体表现为：

- 无法机械回答"PRD 第 X 条实现了没有"；
- 无法判断"这次改动的测试覆盖了哪几条需求"；
- 需求变更时无法定位受影响的代码与测试；
- 验收时只能靠人复述，无法交付追溯证据。

**规范建议**（从最小可行起步）：

1. **给需求编号**：将 PRD 拆为可验证的原子需求，编号 `REQ-GEN-001`（通用）/ `REQ-SCH-014`（排期）/ `REQ-EXP-003`（导出）等。每个需求必须可判定真假——"系统应支持导出"不合格，"系统应支持按分组导出 Word，且导师与学生姓名着色与网页一致"合格。
2. **建立追溯矩阵**（Markdown 表格即可）：

| 需求编号 | 需求摘要 | 设计决策 | 实现位置 | 验证用例 | 状态 |
| --- | --- | --- | --- | --- | --- |
| REQ-COL-001 | 导师姓名在网页与导出恒定同色 | ADR-0003 黄金向量 | `shared/mentor-colors.json`、`src/utils/color.ts`、`api/mentor_colors.py` | `MentorColorSourceTests` | 已验证 |
| REQ-SCH-021 | 不能跨排期版本移动学生 | ADR-0007 写锁 | `api/schedule_integrity.py` | `test_architecture_v2.py` | 已验证 |

3. **明确未实现范围的需求编号**：架构升级说明第 8 节"当前保留的范围"应回填需求编号，使"哪些需求尚未实现"从散文变为清单。

> **注意**：追溯矩阵**不必追求全覆盖**。建议只覆盖硬约束、导出、并发保护、权限这四类高后果需求（约占 30%），其余只做粗粒度归集。全量追溯是重型流程，对当前团队规模不经济。

### 4.3 待改进二：评审从"个人审查"升级为"检查单驱动"

**现状证据**：无法从仓库判断是否存在代码评审流程（无 PR 模板、无 CONTRIBUTING、无评审检查单）。提交历史显示问题多以 `fix: resolve F-XX` 事后修复的形式出现，说明缺陷主要在**测试阶段或使用中发现**，而非评审阶段拦截。

**规范建议**：建立**分层评审检查单**，与 §2.3 的不变式清单直接挂钩。变更类型决定检查项：

| 变更类型 | 必查项 |
| --- | --- |
| 算法/约束变更 | 硬约束全部不变式；属性测试是否覆盖新组合；性能基线是否退化 |
| 导出变更 | Word **与** Excel 两条通道是否同时覆盖；颜色一致性黄金向量是否仍通过 |
| 打包/发布变更 | `DefenseScheduler.spec` 的 `datas` 是否包含新增共享文件；`dist/` 是否已重建 |
| 数据模型变更 | 迁移是否可逆；是否需要演练；老数据兼容性 |
| 前端接口变更 | 前端类型定义与后端序列化器是否同步；Mock 是否同步 |

**这条检查单直接源于本项目两次真实的质量教训**（前端未重建导致 EXE 内是旧界面、共享 JSON 未纳入打包导致运行时缺文件）——两处都恰好落在"单元测试之外"，而检查单正是拦截这类问题的手段。

### 4.4 待改进三：分支与发布策略显式化

**现状证据**：存在 9 个本地/远程分支，含 `backup-before-remove-claude-contributor`、`github-latest-main`、`integrate-latest-backend-fixes` 以及两个 worktree 分支，命名风格不统一且语义不明。

**规范建议**：

1. **分支命名规范化**：`feat/`、`fix/`、`chore/`、`release/` 前缀 + 简短描述；临时备份分支用 `archive/` 前缀并注明归档原因与日期。
2. **明确主干策略**：当前 `main` 为唯一发布分支，建议采用简化 Trunk-Based——短生命周期特性分支合入 `main`，`main` 时刻可发布，版本由 tag 标记。这对单人/小团队最经济，避免引入 Git Flow 的流程开销。
3. **清理策略**：一次性清理已合并或已归档的分支，并保留 tag 作为发布锚点。**清理前须确认无未合并提交**（`git log main..<branch>`）。
4. **发布清单固化为脚本**：将当前的人工发布步骤（构建 → 打包 → EXE 测试 → 计算哈希 → 归档）整理为 `scripts/release.ps1`，与 CI 阶段二共用同一套命令，避免"文档写的"与"实际做的"再次分叉。

### 4.5 待改进四：配置与依赖管理的一致性

**现状证据**：依赖分三份（`requirements.txt` / `-dev` / `-production`），分层清晰；`.env.example` 与 `.env.production.example` 齐备，且 `settings.py` 对生产环境有硬守卫（密钥长度、DEBUG 关闭）。**这部分做得很好。**

**残留风险与建议**：

1. **依赖未锁定**：`requirements.txt` 使用 `==` 固定版本（好），但 `package.json` 使用 `^` 范围。虽然存在 `package-lock.json`，建议在 CI 中统一使用 `npm ci` 而非 `npm install`，并在文档中明确"禁止手工升级依赖版本"。
2. **`.env` 已提交**：根目录存在 `.env`（114 字节）。虽然 `.gitignore` 已忽略 `.env`，但文件确实存在于工作区。建议确认其内容不含真实密钥；若含，应轮换并仅保留 `.env.example`。
3. **环境矩阵未文档化**：Python 3.12、Node 版本、SQLite/PostgreSQL 两种数据库路径，建议在 README 中以表格明确"支持 / 已验证 / 未验证"三档，避免使用者误以为 PostgreSQL 路径已充分验证。

## 6. 需要避免的过度规范化

规范化建议本身也有失效风险。以下三条明确**不建议**当前引入：

1. **不建议为单人/小团队引入重型流程**（Scrum 全套仪式、完整 Git Flow、强制 PR 双人评审）。决策效率的损失会超过质量控制收益。
2. **不建议追求 100% 需求追溯覆盖**。追溯的价值集中在高后果需求，全覆盖的维护成本会迅速吞掉收益，最终导致整份矩阵被废弃。
3. **不建议把覆盖率设成硬性门槛（如 80%）**。在启发式算法项目中，高覆盖率与高风险覆盖是两个概念——追求数字会诱导编写无断言的"过路测试"。覆盖率应当先**可见**，再**按模块**讨论是否设门槛。

## 7. 总结

本项目在**技术质量**上已建立明显优势：结构化的并发保护、单一真相源的配色契约、延伸到交付物本体的验证链。真正的规范化空间不在"做得更好"，而在**治理结构**上补齐三件事：

- **设计视角**：把隐式不变式显式登记，把分层边界从"可阅读"变成"可执行"。
- **SQA 视角**：把"通过"从人工纪律变成不可绕过的门禁；把"用例计数"升级为"风险覆盖"；对启发式算法引入属性测试。
- **开发视角**：建立需求编号与追溯矩阵，把评审从个人经验升级为检查单驱动，使配置与发布流程可复现。

一句话概括：**这个项目已经证明了"能做出高质量的东西"，接下来的规范化目标是"守得住它"**——而守住的关键，不是更多的实践，而是把实践固化为机制。

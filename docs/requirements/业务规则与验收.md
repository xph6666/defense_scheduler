# 业务规则与验收

本清单连接重要业务底线、实现位置和验证入口。政策默认读取 `shared/defense-policy.json`，导师配色读取 `shared/mentor-colors.json`；规则的详细兼容语义见[架构说明](../architecture/架构升级说明.md)。旧 policy/schema 的兼容行为保留在原版本范围内。

下表登记当前设计要求，不表示本次测试已经执行。实际运行结果记录到发布或验证记录，并链接回 [STATUS.md](../../STATUS.md)。

| 编号 | 必须保持的行为 | 实现位置 | 验证入口 |
| --- | --- | --- | --- |
| REQ-SCH-001 | 学生覆盖、分组容量、时间与教室互斥符合所选场景；错误草稿不能发布 | `algorithm.py`、`scheduling/`、`api/schedule_views.py` | `api/test_algorithm_v2.py`、`api/test_architecture_v2.py` |
| REQ-SCH-002 | V2 预答辩至少 4 专家、正式固定 5、中期至少 5，主席计入专家数；秘书另计并满足资格 | `shared/defense-policy.json`、`scheduling/policies.py` | `api/test_algorithm_v2.py`、`scripts/test-frontend-domain.cjs` |
| REQ-SCH-003 | 预答辩／中期导师同组；正式按配置回避指导学生所在组并满足同场；秘书不在指导学生组担任秘书 | `scheduling/`、`api/services/`、`algorithm.py` | `api/test_algorithm_v2.py`、`api/test_architecture_v2.py` |
| REQ-SCH-004 | 联合生成固定引用本轮预答辩；任一阶段失败整体回滚；重复请求保持幂等 | `api/schedule_views.py`、`api/services/schedules.py` | `api/test_architecture_v2.py`、`api/test_stability.py` |
| REQ-SCH-005 | 学生移动不能跨版本，保留或显式重绑秘书遵守本版本关系基线 | `api/schedule_integrity.py`、`api/services/adjustments.py` | `api/test_architecture_v2.py`、`api/test_stability.py` |
| REQ-SCH-006 | 手调带最新 revision；过期写入拒绝；缺少编辑版本号拒绝并回滚 | `api/schedule_integrity.py`、`src/api/` | `api/test_stability.py`、`api/test_architecture_v2.py` |
| REQ-SCH-007 | 发布和归档快照保留历史人员、关系、规则及导出数据，不随基础资料改写 | `api/models.py`、`api/schedule_integrity.py` | `api/test_stability.py`、`api/test_architecture_v2.py` |
| REQ-AUTH-001 | 普通用户读取发布结果，受限写操作只允许管理员；退出撤销 Token | `api/permissions.py`、`api/views.py`、`api/authentication.py` | `api/tests.py`、`api/test_auth_password.py`、`api/test_stability.py` |
| REQ-EXP-001 | 所选版本的网页、Word、Excel 和打印保持导师配色、成员计数与备注语义一致 | `shared/mentor-colors.json`、`api/export_word.py`、`api/services/export_excel.py`、`src/domain/printSchedule.ts` | `api/tests.py`、`scripts/test-frontend-domain.cjs`、`scripts/test-v2-ui.py` |
| REQ-DATA-001 | 导师／秘书使用稳定关系，旧姓名输入兼容，重命名与删除不破坏冻结数据 | `api/models.py`、`api/serializers.py`、`api/services/reference_data.py` | `api/test_data_v2.py`、`api/test_architecture_v2.py` |

## 每项变更的验收

- 先写具体触发条件和预期结果，列出资源不足、空输入、权限或历史版本等相关边界。
- 规则改变同时检查生成、手调、冲突检测和发布，前后端政策转换保持一致。
- 新缺陷保留可复现的最小数据；共享样例放入 `tests/fixtures/`，使用合成或脱敏资料。
- 对随机性或性能优化记录输入规模、种子（若有）、耗时与输出约束；优先验证硬约束。
- 测试条数用于记录执行情况，不能替代业务风险覆盖说明。

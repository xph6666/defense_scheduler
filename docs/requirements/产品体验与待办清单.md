# 产品需求与实施任务清单

整理日期：2026-10-12；更新日期：2026-10-30（北京时间）。

预／正式当前人数、外院组成、生成顺序和教室流程采用[三阶段算法说明](../architecture/三阶段排期算法与优化.md)。与旧 PRD 有差异时按[最新覆盖关系](全量需求追踪.md)验收，不能照搬历史 301 人结果。

当前采用三名开发共同修改、两名测试各自独立进行全系统和全流程测试。开发按实际问题协商认领，不固定个人模块，也不继承之前的人员分工。当前首要目标是修复真实使用中的错误，让操作顺畅，并满足全部已确认需求。

[STATUS.md](../../STATUS.md)只汇总总体进度，人员认领与问题处理放在 Issue／任务记录。全部需求见[全量需求追踪](全量需求追踪.md)，协作和测试分别见[团队职责与任务协作](../guides/团队职责与任务协作.md)、[真实数据全流程测试与验收](../guides/真实数据全流程测试与验收.md)。

## 开发共同要做的内容

1. **修复实际使用中的错误。** 优先解决无法继续操作、数据错误或丢失、生成失败、硬规则错误、发布和导出失败；同时修复两名测试发现的问题。
2. **保证资料和数据关系正确。** 检查导入预览、教师学生维护、导师和参与环节、校区课表及教室资料；错误能指出位置和修正方法，避免重复导入、关系错乱或静默忽略。
3. **保证排期结果正确。** 检查三类答辩与联排、人数和角色、导师关系、时间资源、冲突检测及质量评分，保证生成、调整和发布口径一致，完整名单不漏排、不重复。
4. **把操作流程理顺。** 简化导入、配置、生成、查看、调整、重验、发布和导出；减少重复填写、无意义切换、反复手调及重复检查，入口和下一步清楚。
5. **改善提示、响应和恢复。** 当前类型和数据状态明确；加载等待、保存、报错及重试有反馈，避免卡住、误导和重复提交；不能让用户只能刷新或重做全部操作。
6. **完善页面和导出结果。** 发布版本、历史结果与导出一致，名单、关系、备注、问题标记、配色和版式完整可用，实际打开检查各要求格式。
7. **补齐需求并完成交付验证。** 对照全部 PRD 和体验要求处理遗漏，修复后自测、相互检查代码，并支持两名测试完成真实全量、实际 EXE、升级恢复及最终复测。

以上是共同工作范围，不分配到固定个人。每个具体问题确定一名修复负责人；跨文件或接口修改先沟通。既有 TASK-P01～P13 仅作为历史需求与实现线索，不再作为人员分配依据。

## 两名测试都要做的内容

两个人分别独立测试整个系统，各自用确认后的完整真实数据走完导入到导出的全部流程，覆盖三类答辩、两校区、适用联排和全部其他功能。两人覆盖范围相同，不能一人只测规则、一人只测页面。

除了结果是否正确，也要记录难理解的提示、找不到的入口、重复操作、等待过久、操作后无反馈以及容易误操作的地方。两人各自保存完整测试记录，共用问题清单；修复后分别复测，交付前两人都在同一最终版本完整复测。

具体检查范围、步骤和记录方式见[真实数据全流程测试与验收](../guides/真实数据全流程测试与验收.md)。小样本、删减名单、跳过功能或另一人的通过结论，均不能代替自己完整测试。

## 已确认的需求

- 满足当前 PRD 的全部需求，常用操作简单易懂，高级配置按需展开。
- 一级导航选择预答辩、正式答辩或中期答辩；二级导航显示对应功能模块。
- 公共教师、学生、教室和课表资料设置独立“基础数据”入口，共用一份数据。
- 优先简化生成之后的调整、检查和导出；调整后自动复核，冲突能定位到相关分组。
- 评分只评价排期结果。五项现有软约束加权计分，软件学院评审次数均等单独提示，不计入总分。
- 预答辩默认 3 位评审、可选 5 位，含组长；正式固定 5 位含主席，继承组号、学生与秘书，全部原评审轮换，导师回避且不要求到场；正式外院至多 1 位。中期至少 5 位。
- 先统一安排组长，再补齐教师，最后分配学生；工作量结合学生任务、可用时间与参与组数优化，当前采用确定性排序和受限搜索。
- 缺导师学生进入未安排清单并显示原因，尽量完成其他可行安排。历史教师空白时间可兼容为草稿无额外限制，但必须显式提示未确认，不能把假设视为真实到场确认。
- 预／正式每组学生 5～7 人、以 6 人为主，组内份额和教师次数共同优化；不再限制每位导师每场 2 人。预答辩必要组可有第 2 位外院导师；教室不参与当前预／正式排期，确定时间表后预约。
- 导师颜色只要求同一份排期内互异；其他排期可复用。网页和各导出保持一致，超过 16 色时扩展。

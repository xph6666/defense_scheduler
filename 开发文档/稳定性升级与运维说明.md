# 稳定性升级与运维说明

## 本次升级的使用变化

1. 一键生成产生**草稿**。管理员处理冲突后点击“校验并发布”；存在错误级冲突时不能发布。
2. 已发布和历史版本不能直接修改。重新生成草稿后，旧版仍可从版本列表查看、导出。
3. 普通用户只读取已发布版本。管理员生成新的草稿不会替换普通用户看到的上一份发布结果。
4. 教师、教室的时间无法识别时暂停使用该资源；“有明确限制但本次日期范围内无可用时间”不再视为不限时间。
5. 编辑分组时，学生名单只读；使用“移动学生”在同一版本内调整归属。
6. 页面过期、有人修改了排期或基础资料时，提交会返回冲突提示，需刷新后重新编辑。
7. 真实后端模式统一读取后端规则和冲突检测，不再静默回退到浏览器演示数据。
8. 退出登录会撤销服务器 Token；Token 默认 12 小时失效。连续失败登录会暂时限流。
9. 导出的草稿明确标注“草稿，未发布”。发布快照保留当时的姓名、人员关系、教室、导师职称和分组；后续基础资料变化不修改这些快照。

## 启动和升级

Windows 源码运行：

```powershell
.\scripts\setup-windows.ps1
.\.venv\Scripts\python manage.py createsuperuser
.\scripts\start-windows.ps1
```

已有账号无需再次创建。安装和启动脚本会检查外部命令退出码；启动使用 Waitress。桌面 exe 的下次打包也会使用同一个 Waitress 入口，源码更新不会自动替换已发放的旧 exe。

后端现在会读取项目根目录的 `.env`，已有进程环境变量优先。桌面打包读取 exe 所在目录的 `.env`。不要将生产示例中的占位密钥用于运行。

迁移 `0008_schedule_stability` 新增版本状态、修订号、输入/结果/导出快照、请求去重标识、服务端审计和数据库写锁。对旧数据中的重复版本号重新编号；同类存在多个当前版本时保留最新一个为当前版本。旧历史版本按迁移时仍可取得的资料冻结，**无法恢复升级前已经被删除或改写的信息**。

应用迁移前先执行：

```powershell
.\.venv\Scripts\python manage.py backupdb
.\.venv\Scripts\python manage.py migrate --noinput
```

`backupdb` 使用 SQLite 在线备份接口并执行完整性检查；输出目录包含数据库、SHA-256 清单和应用密钥。目录含敏感资料，应限制访问并复制到另一块受控磁盘。桌面程序在有待执行迁移时自动备份数据库；请同时保留 `app-data/secret.key`。

## SQLite 恢复

1. 停止服务，确认没有仍在使用该数据库的进程。
2. 保留故障现场数据库与相关文件，不直接覆盖唯一副本。
3. 校验备份 `manifest.json` 中的 SHA-256，并对备份运行 `PRAGMA integrity_check`。
4. 将备份数据库恢复到一个新路径，通过 `DJANGO_DB_PATH` 指向该路径；恢复相应的应用密钥。
5. 需要回退程序版本时，同时使用与备份时匹配的代码。需要向前升级时，先对恢复副本执行迁移。
6. 启动后核对学生数量、最新版本及导出内容，再恢复业务访问。

推荐每日自动备份、升级前备份；定期在独立目录执行恢复演练。脚本本身不替代机器上的定时任务和异地备份。

## 多人服务器部署

保持当前单体应用结构，配置 PostgreSQL、受控 HTTPS 反向代理和进程守护：

```powershell
.\.venv\Scripts\python -m pip install -r requirements-production.txt
.\.venv\Scripts\python manage.py migrate --noinput
.\.venv\Scripts\python manage.py collectstatic --noinput
.\.venv\Scripts\python manage.py check --deploy
.\.venv\Scripts\python -m defense_scheduler.server
```

按 `.env.production.example` 设置 `DJANGO_ENV=production`、随机长密钥、允许域名、安全 Cookie、HTTPS 和数据库连接参数。缺失有效密钥或仍开启 DEBUG 时，生产模式拒绝启动。

- 反向代理提供 TLS，静态文件分别指向 `dist/assets` 和 `staticfiles`，其余请求转发到本机 Waitress。
- `DJANGO_TRUSTED_PROXY` 只能设置为受控代理地址。Waitress 仅信任该代理的协议头，供 Django 识别 HTTPS。
- 多进程/多实例部署应配置共享 `REDIS_URL`，登录失败计数不应各进程独立维护；同时在代理层限制登录请求频率。
- PostgreSQL 使用 `pg_dump` 等原生工具备份，`backupdb` 只用于 SQLite。
- `/health/` 返回数据库连通状态，故障返回 HTTP 503；监控应同时检查进程、磁盘空间、备份是否按时完成。
- 应用错误日志位于 `logs/server.log`，自动轮转；服务端业务审计保存在数据库，网页清空日志不会删除它。
- 生产依赖范围应在部署环境安装验证后生成并保存锁定清单。本次没有连接实际 PostgreSQL、Redis 或 TLS 代理进行联调。

## 接口兼容说明

- 排期结果新增 `versionId`、`version`、`revision`、`status`、`isCurrent`。
- 人工调整必须携带 `expected_revision`。缺失返回 428，过期返回 409；被拒绝的提交不保留部分写入。
- 生成请求可携带 `request_key`。同一标识和规则重试返回同一版本；标识与规则不符返回 409。
- 新增 `/api/schedule/versions/`、`/api/schedule/publish/`、`/api/auth/logout/`。
- 结果查询、冲突检查和导出支持指定 `version_id`。
- 普通用户不能读取未发布草稿。

## 后续仍需建设的能力

- 独立的年度/答辩批次及学院数据隔离；当前基础名单仍为全局名单。
- 人员工号关联，替换现有的导师/秘书姓名匹配。
- 持久化后台排期任务、取消和进度。当前生成仍为同步请求，前端超时为 120 秒，并提供幂等重试。
- 复杂约束的全局求解、角色资格和跨校区交通缓冲的完整建模；当前改进为逐组尝试候选时段，不保证找到全局最优解。
- 大规模列表的分页、长期负载与容灾压测。当前数据库写锁优先保证一致性，写操作会串行等待。
- 外院导师集中、学硕优先的真实评分暂未实现，页面会明确标为未评估，不计入总分。

真实样例中仍有借用时间缺失或无法识别的资源。升级会将这些情况暴露为冲突，需业务人员补正后才能发布正式安排。
